# 决策记录

每条决策写明状态、理由和推翻条件。状态分三种：

- **已定**：用户已确认。
- **采纳**：agent 的建议，用户没有异议，可以照此实施。
- **待定**：等待用户确认，相关任务在 PROGRESS.md 中标记 ⏸。

推翻一条决策时，不要删除原条目：把原条目改为“已废弃（被 D-xx 取代）”，再新增一条。

## D-01 平台目标　**已定**

Windows 11 22H2+ x64 为主目标；Windows 10 只求能运行，不投入适配；ARM64 放到阶段 4 之后。

- 理由：用户要求优先 Win11。Windows 10 家庭版的扩展安全更新已于 2026-10-13 结束。
- 影响：Mica、圆角、EcoQoS 等 Win11 能力可以直接使用，不必为 Win10 写降级界面，只需保证不崩溃。

## D-02 进程模型：常驻核心 + 按需界面　**采纳**

常驻的 `taskease-core.exe` 不带界面框架，负责托盘、前台检测、采样、规则执行和 IPC。界面单独一个进程，只在打开窗口或托盘面板时运行，关闭后延迟退出。核心自带守护模式（`--guard`）。需要管理员权限的能力放在可选的 `taskease-svc.exe` 服务里。

- 理由：轻量是核心要求。界面框架（WebView2 或 WinUI）的常驻开销最大，按需启停后，后台只剩一个很小的原生进程。界面进程与核心解耦，D-04 选哪种界面都不影响核心。
- 代价：多一层 IPC；托盘面板冷启动有延迟（由 D-04 的评测控制）。
- 推翻条件：评测显示界面冷启动无法满足 [03 界面方案](Docs/03-UI-Options.md) 的门槛，且常驻界面进程的空闲开销也可以接受。

## D-03 核心语言：Rust + windows-rs　**采纳**

- 理由：无运行时、常驻内存小；`windows-rs` 是微软维护的官方绑定；纯逻辑 crate 能在 macOS 上直接 `cargo test`，方便在 Mac 上工作的 agent。
- 备选：C# .NET 8 Native AOT。如果 D-04 选 WinUI 3，界面层会用 C#，但核心仍保持 Rust，两者通过 IPC 通信。

## D-04 界面方案　**待定（等待用户确认）**

推荐 **Tauri 2 + Svelte 5**，备选 WinUI 3（C#）。完整对比见 [03 界面方案](Docs/03-UI-Options.md)。

- 定案方式：先完成 T0.6 的两个原型并对照评测门槛，用户看过截图和数据后确认。
- 在定案之前，阶段 2 的界面任务全部处于 ⏸。

## D-05 安装方式：按机器安装（Inno Setup）　**采纳**

安装到 `C:\Program Files\TaskEase\`，安装时请求一次 UAC。核心以当前用户身份运行，通过 `HKCU\...\Run` 开机自启。系统服务是可选组件，用户第一次开启网络或帧率统计功能时再安装（再请求一次 UAC）。

- 理由：服务需要确认调用方可信。安装目录只有管理员能写，服务据此认定“这个路径下的 exe 是正版核心”。如果装在用户目录，任何同用户进程都能替换核心，借服务的权限做事。
- 备选：按用户安装且不提供服务，那网络与帧率统计功能将不可用。

## D-06 网络控制技术　**采纳（实施前需通过 V-10、V-11）**

| 能力 | 方案 |
| --- | --- |
| 阻断 | WFP 用户态接口，使用动态会话：服务退出或崩溃时过滤器自动消失 |
| 上下行限速 | WinDivert 2.2（选用 LGPLv3 许可），在服务内按应用做令牌桶整形 |
| 上传限速备选 | 系统自带的基于策略的 QoS，只在 WinDivert 未通过验证时考虑 |
| 按应用网速 | ETW Microsoft-Windows-Kernel-Network，在服务内采集 |

- 详见 [07 网络](Docs/07-Network.md)。

## D-07 帧率限制技术　**采纳（实验功能，实施前需通过 V-08、V-09）**

- 主方案：向用户逐个开启的目标应用注入 DLL，挂钩呈现调用（DXGI `Present`、Vulkan `vkQueuePresentKHR`、OpenGL `SwapBuffers`），按核心写入共享内存的目标帧率等待。前后台切换时目标帧率实时变化。
- 辅助手段：GPU 调度优先级（`D3DKMTSetProcessSchedulingPriorityClass`），不需要注入，但它只在 GPU 资源争抢时起作用，不能保证帧率上限。
- 后续可选：NVIDIA 驱动配置文件的“最大帧速率”。它只在应用启动时生效，不能随前后台切换。
- 默认关闭。每个应用需要单独开启，界面明确提示有被反作弊或安全软件拦截的风险。
- 详见 [06 帧率](Docs/06-FrameRate.md)。

## D-10 代码签名　**采纳（初期）**

初期不签名，在发布说明和 README 中告诉用户如何越过 SmartScreen（“更多信息 → 仍要运行”）。阶段 4 评估 SignPath Foundation 开源签名计划和 Azure Trusted Signing 的申请条件（V-15）。注入 DLL 和 WinDivert 相关功能在未签名时被安全软件拦截的概率更高，这是已知风险。

## D-11 CPU 温度　**采纳**

首版不显示 CPU 温度：Windows 没有公开接口，读取需要内核驱动。只显示 GPU 温度（如果驱动提供）和系统热区信息（V-06 验证可用性）。后续如需 CPU 温度，单独评估 PawnIO 等方案。

## D-12 发布与 macOS 共存　**采纳**

- Windows 版使用独立版本号（从 0.1.0 开始），标签为 `win-v0.1.0` 这种格式，发布时不标记为 “Latest”。
- macOS 版的 `GitHubClient.latestRelease()` 读取的是 `/releases/latest`，并筛选 `.dmg` 资源。只要 Windows 版不被标为 Latest，就不受影响。
- 第一次发布 Windows 版之前（T4.6），要确认 macOS 更新检查不会误读 Windows 版本；必要时改为“列出 releases 并按标签前缀过滤”，这一项需要用户同意。

## D-13 CPU 限制实现：Job 硬上限，保留轮流暂停作为备选　**采纳（需通过 V-03）**

- 默认用 Job Object 的 CPU 硬上限，由内核执行，平滑且开销低。
- 如果 V-03 发现 Job 嵌套失败或恢复风险过高，改用 macOS 的做法：按额度轮流暂停和恢复（`BudgetCredit`）。
- 详见 [05 进程控制](Docs/05-ProcessControl.md)。
