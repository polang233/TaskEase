# 03 界面方案

在 D-02 的架构下，界面是一个**按需启动的独立进程**：核心常驻且不带界面框架，所以界面框架的开销只在窗口打开期间存在。这让“轻量”和“好看”可以兼顾，选择界面方案时主要看三点：外观还原度、打开速度和实施成本。

## 候选方案

| 方案 | 技术 | 外观还原 macOS 版 | 原生感（Win11） | 打开时内存（估计） | 冷启动 | 与 Rust 核心集成 | 许可 | agent 实施难度 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| **A. Tauri 2** | Rust + WebView2 + Svelte 5 | ★★★★★ 可以几乎复刻 | ★★★ Mica 可用，控件需要自绘 | 80–150 MB（含 WebView2 子进程） | 0.3–0.8 s | ★★★★★ 同语言，类型可直接导出 | MIT/Apache | 低：前端生态成熟 |
| **B. WinUI 3** | C# + Windows App SDK | ★★★ 神似，Fluent 风格 | ★★★★★ 原生控件、Mica、动画 | 60–120 MB | 0.5–1.2 s | ★★★ 需要用 IPC 与 C# 类型互转 | MIT | 中：XAML 资料较少，打包细节多 |
| C. Slint | Rust 原生自绘 | ★★★★ | ★★ 没有 Mica 等系统材质 | 15–40 MB | < 0.2 s | ★★★★★ | GPLv3 可选 | 中：生态小，复杂动画要手写 |
| D. Qt 6 / QML | C++ 或 Rust 绑定 | ★★★★ | ★★★ | 40–80 MB | 0.3–0.6 s | ★★ | LGPLv3 | 高：构建与部署复杂 |
| E. Avalonia | C# 自绘 | ★★★★ | ★★★ | 60–100 MB | 0.5–1 s | ★★★ | MIT | 中 |
| F. Win32 + Direct2D 自绘 | C++/Rust | ★★★★★ | ★★★★ | 10–20 MB | < 0.1 s | ★★★★ | — | 极高：每个控件、文字输入、无障碍都要自己做 |
| G. Electron | Node + Chromium | ★★★★★ | ★★ | 150–300 MB | 1–2 s | ★★ | MIT | 低 |
| H. Flutter | Dart 自绘 | ★★★★ | ★★ | 60–120 MB | 0.4–0.8 s | ★★ | BSD | 中 |

表中的内存和启动时间是同类应用的经验值，不是本项目的实测结果，T0.6 会实测 A 和 B。

**排除**：

- G（Electron）：常驻开销和安装体积与“轻量”定位冲突。
- F：实施成本过高。
- D、E、H：没有明显优势，又多引入一门语言或一套工具链。

## 推荐：A. Tauri 2 + Svelte 5

**理由**：

1. **外观最接近 macOS 版。** 用户最担心的是 Windows 版看起来差很多。用 CSS 可以按 macOS 版的截图逐项还原：圆角卡片、渐变选中态、圆环概览、带动画的悬停卡片和分段控件，同时用 `window-vibrancy` 给窗口加上 Mica 背景，融入 Win11。
2. **与核心同语言。** IPC 消息类型从 te-model 直接导出为 TypeScript，不用手工同步两套类型。
3. **轻量问题由架构解决。** 窗口打开时 WebView2 的开销确实比 WinUI 高，但界面关闭 2 分钟后进程会退出，常驻开销只剩核心。WebView2 是 Win11 自带的运行时，安装包只有几 MB。
4. **agent 的实施成功率高。** Web 前端资料最多，视觉上也最容易逐像素对照。

**代价与对策**：

| 代价 | 对策 |
| --- | --- |
| 托盘面板冷启动有延迟 | 托盘右键菜单用核心的原生菜单，立即弹出；左键面板第一次打开时允许不超过 0.8 秒，之后 2 分钟内保活，再次打开不超过 150 ms |
| 原生细节（焦点、滚动、右键菜单、无障碍）需要自己补 | 在 [界面规范](#界面规范) 中列出必须做的项目，作为验收条目 |
| WebView2 子进程会出现在任务管理器里 | 子进程计入 TaskEase 自身占用，在应用列表里如实显示 |

**选 B（WinUI 3）的情况**：如果用户更看重“像系统自带应用”，而不是和 macOS 版长得一样；或者 T0.6 测出 Tauri 冷启动超过门槛。

## T0.6 评测（决策门）

用同一份夹具数据，分别做 A 和 B 两个原型。每个原型都包含：

- 管理窗口：概览条、约 300 行的应用列表（每秒刷新）、详情与规则卡片、分段控件、滑块和开关。
- 托盘面板：占用前五的应用和概览。
- 一张悬停卡片：从一个指标滑到另一个指标时，交叉淡入淡出。

只接夹具，不接核心。

| 指标 | 门槛 | 测法 |
| --- | --- | --- |
| 冷启动到窗口可见 | ≤ 800 ms | 从进程创建到第一帧可见，取 5 次中位数 |
| 保活状态下打开托盘面板 | ≤ 150 ms | |
| 窗口打开时私有内存总和（含子进程） | ≤ 150 MB | 任务管理器“详细信息”中的私有工作集之和 |
| 列表每秒刷新时 CPU | ≤ 单核的 2% | 1 分钟平均 |
| 滚动与悬停动画 | 60 Hz 屏幕上不掉帧 | PresentMon 或人工观察 |
| 视觉对照 | 用户主观评价可以接受 | 把浅色和深色截图与 [macOS 截图](../../Artifacts/screenshots/management.jpg) 并排 |

把结果写进 `Windows/Artifacts/local/ui-bakeoff/`，在 PROGRESS.md 中附上摘要，交给用户确认 D-04。

## 界面规范

以下要求与方案无关。

### 视觉

- 品牌色 `#30BBA9`。十档占用配色直接取 `TaskEase/Shared/Views/MetricPalette.swift` 中的浅色和深色色值，阈值与 [../../Docs/SystemMetrics.md](../../Docs/SystemMetrics.md) 一致。
- 字体：
  - 西文用 `Segoe UI Variable`。
  - 简体中文用 `Microsoft YaHei UI`，繁体中文用 `Microsoft JhengHei UI`。
  - 数字使用等宽数字（`font-variant-numeric: tabular-nums`），数值变化时整行不会左右移动。
- 窗口：
  - 背景用 Mica。
  - 标题栏内容延伸进窗口，右侧保留系统的最小化、最大化和关闭按钮。
  - 页眉中可拖动的区域只有品牌区和空白处，与 macOS 版 `WindowHeaderDrag` 的约定一致。
- 圆角：卡片 8 px，控件 4 px（Win11 规范）。
- 深浅色：跟随系统、浅色、深色三种，由核心统一下发，界面不要自己读系统主题。

### 托盘

- 图标用单色图，浅色和深色各一套，跟随任务栏主题（`SystemUsesLightTheme`），不跟随应用主题。
- 点击行为：
  - 左键打开面板。
  - 右键打开原生菜单：打开管理窗口、启用或暂停限制、退出。
- 面板贴着任务栏通知区弹出，要适配任务栏在上下左右四个位置、多显示器和不同 DPI。失去焦点时关闭面板。
- 首次运行：如果检测到图标在溢出区，显示一次引导，教用户把图标固定到任务栏。

### 交互

- 悬停卡片沿用 macOS 的行为：指针移上去约 0.16 秒后出现，相邻指标之间滑动切换，点击固定。卡片不能被窗口边界裁掉。
- 键盘：Tab 顺序合理，列表可以用方向键选择，Esc 关闭卡片和面板。
- 无障碍：控件要有可访问名称；界面测试按名称和 `automation id` 查找元素。
- 文案：键名和内容取自 `TaskEase/Resources/Localizable.xcstrings`。Windows 独有的文案用 `win.` 前缀新建键。
